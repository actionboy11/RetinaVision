# RetinaVision AI 服务稳定性与可观测性设计

## 1. 目标

在不引入 Prometheus、Grafana 和新监控数据库表的前提下，为 RetinaVision 的 Java 后端、Python AI 服务和现有 Dashboard 建立轻量、可长期运行的稳定性与可观测性能力。

本轮同时支持：

- Windows 本机 Conda 环境常驻运行；
- Docker 容器运行；
- 单任务串行推理；
- Python 进程级实时状态；
- Java 聚合健康状态；
- 基于现有任务数据库的长期业务指标；
- Dashboard 系统状态展示；
- Java 与 Python 两端的结构化调用日志。

## 2. 非目标

本轮不实施：

- Prometheus、Grafana 或外部日志平台；
- 新增监控数据库表；
- 多 GPU 调度和多模型并行；
- 模型重新训练、模型结构或权重修改；
- Windows 系统服务的自动注册；
- 高频自动轮询或自动告警通知。

## 3. 总体架构

业务推理链路保持不变：Java Worker 从 RabbitMQ 消费任务，通过 HTTP 调用 Python AI，保存结果，并使用现有有限重试与死信恢复机制处理失败。

新增独立观察链路：

1. Python `/health` 报告模型和当前进程的实时状态。
2. Java 使用独立短超时调用 Python 健康接口。
3. Java 聚合 AI 状态、RabbitMQ 队列状态和数据库任务统计。
4. Dashboard 只访问 Java 的聚合接口，不直接访问 Python。

一个依赖发生故障时，聚合接口仍返回其他可用组件的信息，避免单点故障导致整个 Dashboard 无法加载。

## 4. Python AI 服务设计

### 4.1 单任务串行推理

Python 进程使用一个进程内串行控制器保护模型调用。同一进程同一时间只允许一个请求进入 PyTorch 推理，后续请求等待锁释放。

无论成功、输入错误、推理异常还是结果保存失败，都必须在 `finally` 路径释放锁。当前 Uvicorn 部署固定单 Worker；多 Worker 会各自加载模型并绕过进程内串行保证，因此启动脚本和容器启动命令不得配置多个 Worker。

### 4.2 健康状态

保留 `GET /health`，扩展响应字段：

```json
{
  "status": "UP",
  "ready": true,
  "modelLoaded": true,
  "modelName": "FSCNet_Final_DMI",
  "modelVersion": "model_new-v1",
  "device": "cuda:0",
  "busy": false,
  "startedAt": "2026-06-19T18:00:00+08:00",
  "totalRequests": 12,
  "successCount": 11,
  "failureCount": 1,
  "lastInferenceTimeMs": 1834,
  "lastSuccessAt": "2026-06-19T18:20:00+08:00",
  "lastError": null
}
```

语义：

- `status=UP`：进程已启动且模型已加载；
- `ready=true`：服务具备处理推理请求的条件；
- `busy=true`：当前有请求持有推理锁；
- 计数和最近状态属于当前 Python 进程，重启后清零；
- `startedAt` 用于区分不同进程生命周期；
- 模型加载失败时应用启动失败，不提供虚假的健康状态。

### 4.3 运行指标

Python 内存中维护线程安全的进程级快照：请求总数、成功数、失败数、当前忙碌状态、最近推理耗时、最近成功时间和最近错误摘要。

长期成功率、失败率和平均处理耗时不从 Python 进程计数推导，而是继续使用 Java 端现有 `analysis_task` 数据，确保进程重启后业务指标不丢失。

### 4.4 请求关联与日志

Java 正式推理请求携带 `X-Request-ID`。Python 优先使用该值；缺失时生成 UUID。

每次请求记录一条开始日志和一条结束日志，至少包含：

- `requestId`；
- 文件名和文件大小；
- 模型名称、版本和设备；
- 排队等待时间；
- 模型推理耗时；
- HTTP 请求总耗时；
- 成功或失败；
- 规范化错误类型。

日志不得记录图像内容、认证信息或不必要的绝对文件路径。

### 4.5 异常隔离

输入格式问题返回 4xx；模型推理和结果存储等内部问题返回 5xx。所有失败更新进程失败计数和最近错误，但不得使后续合法请求失去推理能力。

## 5. Java 后端设计

### 5.1 正式推理超时

保留现有正式推理超时：连接超时 5 秒，读取超时 5 分钟。该超时覆盖上传、模型推理和响应读取，不与健康探测共用客户端配置。

### 5.2 AI 健康探测

新增独立 AI 健康客户端，调用 `GET /health`，默认连接超时 2 秒、读取超时 3 秒。

健康探测失败不得抛出到 Dashboard，而是转换为结构化 `DOWN` 状态，并保留简短错误原因。正式推理客户端和健康客户端使用不同超时，避免 AI 卡顿拖住系统状态查询。

### 5.3 系统状态聚合接口

新增：

```http
GET /api/system/status
```

接口供所有已登录用户访问，聚合：

- AI 实时状态；
- RabbitMQ 主队列与死信数量；
- 数据库长期任务成功率、平均耗时、失败数和重试数；
- 汇总状态和检查时间。

组件状态使用 `UP`、`DEGRADED`、`DOWN`。汇总规则：

- AI、RabbitMQ 和数据库均正常：`UP`；
- 业务仍可查询但任一外部依赖异常：`DEGRADED`；
- 数据库不可用或聚合接口无法形成有效响应：由统一异常处理返回服务错误，不伪造 `UP`。

AI 或 RabbitMQ 单独不可用时，接口返回 HTTP 200，并在对应组件中标记 `DOWN`，其他组件数据继续返回。

### 5.4 Java 调用日志与错误分类

Java 正式推理调用和结果下载沿用同一个 `requestId`，日志至少包含：

- `taskId`、`taskNo`、`requestId`；
- 当前重试次数；
- 调用阶段；
- HTTP 状态；
- 推理接口总耗时；
- 结果图下载耗时；
- 错误分类。

错误分类固定为：连接失败、读取超时、AI 4xx、AI 5xx、返回体不完整、结果地址不可信、结果下载失败和未知错误。

## 6. Dashboard 设计

Dashboard 新增“系统运行状态”区域，展示：

- 总体状态；
- AI 服务状态和忙碌状态；
- 模型名称、版本和运行设备；
- 当前进程启动时间与最近推理耗时；
- 最近 AI 错误摘要；
- RabbitMQ 消费者、等待消息、未确认消息和死信数量；
- 数据库任务成功率、平均处理耗时、失败数和重试数。

页面沿用现有手动刷新行为，本轮不增加自动轮询。系统状态请求失败时只影响该区域，不清空已有任务趋势和统计数据。

## 7. 部署设计

### 7.1 Windows Conda

提供 PowerShell 启动、停止和健康检查脚本，固定使用：

```text
C:\develop\anaconda3\envs\retinavision-ai\python.exe
```

启动脚本检查 Python、模型权重、必要目录和 8000 端口，配置模型、存储及日志目录，以单 Uvicorn Worker 启动服务。日志写入独立目录。

README 说明如何由用户自行注册为 Windows 常驻服务，但脚本不自动修改系统服务配置。

### 7.2 Docker

AI 项目增加 Dockerfile 和 `.dockerignore`。权重通过只读 Volume 挂载，结果与日志目录通过可写 Volume 挂载。容器配置 `/health` 健康检查，并以单 Worker 运行。

Compose 中 Java 使用服务名访问：

```text
http://retinavision-ai:8000
```

默认提供 CPU 可运行配置；CUDA 部署只记录环境变量、设备映射和镜像替换说明，不绑定某个特定 CUDA 版本。

## 8. 安全与降级

- Dashboard 和浏览器不直接访问 Python。
- `/api/system/status` 需要登录，但不限制为管理员。
- 健康响应不暴露权重绝对路径、堆栈、环境变量或敏感凭据。
- 最近错误仅保留适合运维展示的摘要。
- AI 健康探测失败不会触发任务重试；只有真实任务执行失败才进入现有有限重试流程。
- 不在本轮引入自动熔断，避免健康探测的瞬时故障阻止真实任务恢复。

## 9. 测试与验收

### 9.1 Python

- 健康响应包含新增字段；
- 同一时间只有一个请求进入模型推理；
- 成功和失败指标正确更新；
- 异常后锁一定释放；
- Java 请求 ID 被保留，缺失时自动生成；
- 健康响应不泄露敏感路径。

### 9.2 Java

- 健康客户端使用独立短超时；
- AI 正常、忙碌、超时和不可达状态正确转换；
- RabbitMQ 异常时聚合接口仍返回 AI 和数据库状态；
- AI 异常时聚合接口仍返回 RabbitMQ 和数据库状态；
- 正式推理日志具备请求关联和错误分类；
- 现有有限重试与死信恢复测试继续通过。

### 9.3 前端

- `UP`、`BUSY`、`DEGRADED` 和 `DOWN` 状态正确显示；
- 系统状态区域失败不影响原有 Dashboard 统计；
- TypeScript 类型检查和生产构建通过。

### 9.4 全链路

- Windows Conda 正常启动并通过健康检查；
- Docker 正常启动并通过容器健康检查；
- 正常推理成功并产生关联日志；
- 停止 AI 后 Dashboard 显示降级，任务进入有限重试；
- 恢复 AI 后任务可继续成功；
- 达到重试上限后进入死信，并可由管理员恢复。

## 10. 完成标准

以下条件全部满足才视为本轮完成：

1. Python 串行推理和运行状态测试通过；
2. Java 健康聚合和错误分类测试通过；
3. Dashboard 能展示系统状态且构建通过；
4. Windows 与 Docker 启动方式均有可执行配置和文档；
5. Java、Python、前端现有测试没有回归；
6. 不修改模型结构、权重和既有任务消息契约。
