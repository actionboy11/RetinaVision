# RetinaVision 领域模块化架构设计

日期：2026-07-28

## 1. 背景与目标

RetinaVision 已具备 Vue 管理端、Spring Boot 业务后端和 FastAPI AI 推理服务，并已打通病例、图像、质量检测、血管分割、异步任务、医生审核、报告签发、随访对比、AI 质控和知识助手等业务链路。

下一阶段的主要目标不是继续增加医疗 AI 功能，而是把现有系统演进为接近商业软件标准的全栈工程样板，用于系统学习现代软件开发中的模块边界、依赖倒置、可靠消息、契约治理、可观测性和分层测试。

本设计采用“领域模块化单体 + 端口适配器”路线。Java 业务后端保持单进程和单数据库部署，Python AI 服务因运行时和资源需求不同继续独立部署。现有浏览器公共 API、枚举、响应结构和核心业务语义保持兼容。

## 2. 设计原则

1. 按业务能力划分模块，不再以 Controller、Service、Mapper 等技术类型作为系统最高层边界。
2. 业务规则位于领域层，领域层不依赖 Spring、MyBatis、RabbitMQ、Redis、HTTP 或文件系统。
3. 外部系统通过端口接入，基础设施代码实现端口。
4. 模块只公开应用接口和事件模型，不公开内部 Entity、Mapper 或数据库表。
5. 优先使用模块化单体控制复杂度，不为学习微服务而提前引入分布式事务和服务治理。
6. 渐进迁移，不一次性重写，不改变未经批准的公共契约。
7. 通过自动化架构测试和契约测试防止边界退化。

## 3. 业务模块边界

### 3.1 identity

负责注册、登录、JWT、退出登录、用户角色和医生职业身份。

该模块向其他模块提供当前主体、角色和医生身份查询能力，但不向外暴露用户持久化模型。

### 3.2 case-management

负责病例、眼底图像、病例归档、图像生命周期和病例对象级访问权限。

该模块拥有病例和原始图像元数据。创建分析任务时调用 `analysis` 的公开应用接口，不直接写任务表。

### 3.3 analysis

负责图像质量检测、血管分割、任务生命周期、结果持久化、失败重试和 AI 推理调用。

该模块拥有任务状态机和分析结果。RabbitMQ 消费者只是基础设施入口，必须调用应用用例完成执行，不得自行实现状态流转。

### 3.4 clinical-workflow

负责人工反馈、修正版本、医生审核和医生待办提醒。

该模块保存临床复核事实，但不直接修改原始分析结果。修正结果以版本形式保留，审核操作必须关联操作者身份和审计时间。

### 3.5 reporting

负责报告草稿、LLM 辅助草稿、PDF 生成、签发和历史版本。

该模块只接受满足审核前置条件的结果。签发前必须重新校验审核状态、医生身份和必要意见的完整性。

### 3.6 knowledge

负责知识文档、索引治理、向量检索、RAG 会话和引用来源。

知识助手不得直接读取患者图像或绕过临床工作流生成正式诊断。

### 3.7 operations

负责聚合统计、系统状态、模型效果评估、风险提醒和死信恢复。

该模块主要消费领域事件或读取专用统计投影，不反向修改核心临床数据。需要恢复任务时，必须调用 `analysis` 的恢复用例。

### 3.8 shared-kernel

仅保存多个模块确实共同依赖且语义稳定的基础类型，例如统一 ID、时钟抽象、分页值对象和错误分类。

业务 DTO、持久化 Entity、模块枚举和通用工具不得因方便而放入 shared-kernel。

## 4. 模块内部结构

每个 Java 业务模块采用以下内部结构：

```text
module/
  api/             # Controller、HTTP 请求和响应模型
  application/     # 用例、事务边界和跨端口编排
  domain/          # 聚合、值对象、状态机、领域服务和领域事件
  infrastructure/  # MyBatis、MQ、Redis、HTTP、文件存储等实现
```

依赖方向固定为：

```text
api -> application -> domain
infrastructure -> application/domain
```

`domain` 不得反向依赖其他层。`application` 定义所需端口，`infrastructure` 提供实现。Controller 只处理认证主体、传输层校验和统一响应，不直接访问 Mapper。

## 5. 核心数据流

主链路为：

```text
case-management
  保存图像
      |
      v
analysis
  创建质量检测任务和待发布事件
      |
      v
Outbox 发布器 -> RabbitMQ
      |
      v
analysis 消费入口
  执行任务 -> AI 端口 -> 产物存储端口 -> 保存结果
      |
      +-- 成功事件 -> clinical-workflow 创建待办
      |
      +-- 失败事件 -> operations 创建风险投影
```

### 5.1 强一致性

任务记录、初始状态和 Outbox 事件在同一数据库事务中提交。需要在一个模块内同步满足的不变量使用本地事务，不通过 MQ 拼接事务。

### 5.2 最终一致性

跨模块通知、统计投影、风险提醒和后续待办通过事件驱动更新。消费者必须支持重复投递，不能假设消息只到达一次。

### 5.3 幂等性

消息使用 `taskId + eventType + eventVersion` 作为幂等标识。外部 AI 调用、结果落库、待办创建和报告生成均需定义重复执行语义。

### 5.4 模块协作

同步协作通过公开应用接口完成；异步协作通过版本化领域事件完成。模块不得跨边界注入对方 Mapper，也不得以直接读写对方表作为常规集成方式。

## 6. 核心端口

`analysis` 至少定义：

- `AiInferencePort`：执行质量检测或血管分割。
- `ArtifactStoragePort`：保存和读取原图、mask 与中间产物。
- `TaskEventPublisher`：发布任务领域事件。
- `TaskRepository`：持久化任务聚合。
- `AnalysisResultRepository`：持久化分析结果。
- `Clock`：提供可测试的业务时间。

`reporting` 至少定义：

- `ReportDraftGeneratorPort`：调用 LLM 生成辅助草稿。
- `ReportRendererPort`：生成 PDF。
- `ReportStoragePort`：保存签发报告。

端口描述业务需要，不暴露具体供应商、HTTP 路径、MyBatis 类型或 SDK 类型。

## 7. 任务状态机

任务状态流转集中到领域模型，任何数据库更新都必须由合法状态转换产生。

```text
CREATED -> WAITING -> RUNNING -> SUCCESS
                         |
                         +-> FAILED

FAILED -> WAITING
CREATED/WAITING -> CANCELED
```

每次状态变化生成审计记录。状态转换同时返回需要发布的领域事件，应用层负责持久化状态、日志和 Outbox 事件。消费者不得通过通用更新方法任意写入状态。

## 8. 前端架构

前端从以文件类型为中心的目录逐步演进为以业务功能为中心：

```text
src/
  app/                 # 启动、路由、全局状态和请求配置
  features/
    cases/
    analysis/
    clinical-review/
    reporting/
    knowledge/
    operations/
  shared/
    api/
    components/
    composables/
    types/
    utils/
```

每个 feature 保存自己的 API、类型、组合式函数、局部组件和页面。页面负责布局和用例协调，不承担所有请求、轮询、权限、表单状态和展示细节。

`TaskDetail.vue` 优先拆分为结果查看、质量摘要、历史对比、人工修正、医生审核和报告签发等独立功能单元。轮询、Object URL 生命周期、提交互斥和错误处理进入可复用 composable。

角色和对象权限通过集中策略函数判断，页面不散落角色字符串和重复条件。`src/utils/request.ts` 继续作为统一 HTTP 入口。

后端 OpenAPI 作为机器可读契约，用于生成或校验 TypeScript 类型；`API_CONTRACT.md` 保留为面向开发者的公共接口说明。两者必须由自动化检查保持一致。

## 9. Python AI 服务架构

Python AI 服务继续独立部署，并采用以下内部结构：

```text
retinavision_ai/
  api/             # FastAPI 路由和 schema
  application/     # 推理用例
  domain/          # 推理结果和质量规则
  inference/       # PyTorch 模型、预处理和后处理
  infrastructure/  # 文件存储、运行状态和配置
```

Python 只处理推理，不感知病例、用户、审核、报告或浏览器 JWT。

模型通过统一的 `SegmentationModel` 接口接入，使真实模型、测试替身和未来模型版本可替换。预处理、滑窗重建、阈值和后处理是独立可测试组件，不隐藏在 FastAPI 路由中。

Java 与 Python 之间增加契约测试，覆盖 camelCase 字段、错误状态、20 MB 限制、文件字段名、结果类型和 artifact URL 安全规则。

## 10. 错误模型

错误分为四类：

1. 业务拒绝：状态不允许、质量门控未通过、报告尚未审核等，返回稳定业务码。
2. 输入错误：字段、内容类型、文件大小和图像解码错误，不进入任务队列。
3. 暂时故障：AI、RabbitMQ、Redis 或存储短暂不可用，可以按明确策略恢复。
4. 确定失败：模型错误、非法产物地址或超过重试上限，进入失败或死信恢复流程。

公共 HTTP 保持现有 `ApiResponse<T>` 和错误码契约。内部错误携带错误分类、可重试标志和安全消息，但不向浏览器暴露堆栈、本地路径、凭据或患者信息。

外部调用配置连接超时、读取超时、有限重试和熔断。只有明确可恢复且操作具备幂等性的错误允许自动重试。

## 11. 可靠性设计

- 使用 Transactional Outbox 避免数据库事务成功而 MQ 消息丢失。
- 消费者使用手动 ACK，并基于错误分类决定 ACK、requeue 或死信。
- 报告签发、人工修正和审核使用乐观锁，防止并发覆盖。
- 文件写入采用临时文件、内容校验和同文件系统原子移动。
- 任务重试保留原任务身份和完整审计信息，不创建无法关联的孤立结果。
- 所有外部调用携带 `traceId`、业务对象 ID 和幂等键。
- 数据库迁移继续统一使用 Flyway，并为已有数据环境提供向前迁移。

## 12. 可观测性

浏览器请求、Java 用例、MQ 消息和 Python 推理共享关联标识。日志采用结构化格式，至少包含模块、用例、traceId、任务 ID、耗时、结果和安全错误分类。

系统指标至少包括：

- HTTP 请求量、错误率和延迟。
- 数据库连接池使用率和慢查询。
- MQ 发布失败、积压量、消费延迟、重试和死信数量。
- Outbox 未发布数量和最长滞留时间。
- 任务成功率、失败原因和端到端耗时。
- AI 推理排队时间、执行时间、模型版本和设备状态。
- 磁盘容量与产物增长速度。

健康检查区分存活、就绪和依赖健康。告警必须关联处置说明，优先覆盖队列持续积压、AI 连续失败、磁盘空间不足和 Outbox 长时间未发布。

## 13. 测试架构

### 13.1 领域单元测试

不启动 Spring，覆盖任务状态机、质量门控、审核、签发、版本和重试规则。

### 13.2 应用用例测试

使用内存端口或测试替身，验证权限、编排、幂等和失败分支。

### 13.3 适配器集成测试

使用 Testcontainers 验证 MySQL、RabbitMQ、Redis、Flyway 和持久化映射。文件存储使用受控临时目录。

### 13.4 契约测试

验证浏览器到 Java、Java 到 Python 的路径、字段、枚举、错误码和二进制响应规则。

### 13.5 前端测试

覆盖表单校验、权限状态、加载与错误状态、轮询清理、Object URL 释放和防重复提交。

### 13.6 端到端测试

仅保留少量高价值路径，至少覆盖“上传图像—质量检测—血管分割—医生审核—报告签发”和失败重试路径。

### 13.7 架构测试

使用 ArchUnit 强制执行：

- 领域层不依赖 Spring、MyBatis、RabbitMQ 或 Web 类型。
- Controller 不依赖 Mapper。
- 模块不访问其他模块的 infrastructure 包。
- 只有 application 层可以协调多个端口。
- shared-kernel 不包含具体业务实现。

### 13.8 AI 测试

预处理、滑窗覆盖、重建、阈值、后处理和模型加载分别测试。真实权重测试作为受环境约束的冒烟测试，不替代快速单元测试。

## 14. 渐进迁移

### 阶段一：建立架构基线

记录模块边界和关键 ADR，引入 ArchUnit，建立当前依赖基线。新增规则先阻止进一步恶化，再逐步收紧，不要求一次修复所有历史依赖。

### 阶段二：迁移 analysis 纵向切片

以分析任务为模板，提取任务状态机、AI 端口、存储端口、仓储接口和 MQ 应用入口。保持现有 HTTP API、队列名称和数据库结构兼容。

### 阶段三：可靠事件与可观测上下文

引入 Outbox、幂等消费、统一 traceId 和结构化日志。完成任务创建、执行、重试与死信恢复的可靠性验证。

### 阶段四：迁移临床闭环

依次迁移 `clinical-workflow`、`reporting` 和 `case-management`。每次只迁移一个可验证用例，禁止同时进行无关功能开发。

### 阶段五：整理前端与 Python

按 feature 拆分大型 Vue 页面，建立 OpenAPI 类型检查；重组 Python 内部分层并增加 Java—Python 契约测试。

## 15. 完成标准

架构演进达到以下条件时视为完成：

- 七个业务模块具有明确所有权和公开边界。
- 核心领域规则可以在不启动框架的情况下测试。
- Controller、MQ 消费者和定时任务都只作为应用用例入口。
- AI、LLM、存储、MQ 和时间均通过端口接入。
- 任务创建与 MQ 发布不存在已知双写窗口。
- 重复消息不会生成重复结果、待办或报告。
- 架构测试能阻止新的跨模块 Mapper 依赖。
- 浏览器公共 API 与现有契约保持兼容。
- 关键业务链路具备跨服务关联日志、指标和少量端到端测试。
- 文档、源码、数据库迁移和自动化验证命令保持一致。

## 16. 非目标

本阶段不包含：

- 将 Java 模块拆成独立微服务。
- 引入第二套消息队列或 Web 后端框架。
- 更换现有前端技术栈。
- 新增疾病诊断模型或宣称临床诊断能力。
- 一次性重写全部前后端代码。
- 为追求目录形式而移动模型权重或运行时医疗数据。

## 17. 迁移风险与控制

- 当前后端仓库存在大量未提交修改。实施前必须先确认基线，任何迁移都不得覆盖这些修改。
- 模块化过程中容易把原有跨表查询简单搬入 shared-kernel。应使用专用查询投影或明确的模块应用接口。
- Outbox 会增加表、发布器和清理策略，需要同时验证数据库迁移、监控和故障恢复。
- 前端页面拆分可能引入重复请求和状态不同步，应先提取用例级 composable 再拆展示组件。
- Python 包移动可能影响模型加载路径和脚本，应保持外部启动命令与 HTTP 契约不变，并以契约测试验证。
